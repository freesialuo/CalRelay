# 从用户故事到可验证实现

Issue 先说明“作为谁，希望什么，以便获得什么结果”，再用 AC 编号写验收条件。采用 INVEST 检查实现项是否可独立验收、可协商、有价值、可估计、足够聚焦且可测试；大范围父 Issue 保留为整体目标，用原生子 Issue 分解，依赖不能伪装成独立性。

## V-Model

| 设计侧 | 对应验证侧 | 需要保留的证据 |
| --- | --- | --- |
| 用户目标与验收条件 | 验收测试 | 正常、失败、边界场景的可观测结果 |
| 系统边界与非功能约束 | 系统测试 | 来源隔离、数量预算、持久性等实际检查 |
| 模块接口与事务边界 | 集成测试 | 真实数据库、模拟外部服务、并发和故障注入 |
| 局部规则与类型设计 | 单元/规则测试 | 不变量、错误类型和边界；不复制实现写断言 |

每个 AC 指向可执行验证；测试失败应能追溯到需求。测试层级按风险选择，不为填满四层而重复测试。协议选型先固定输入及预期，再试候选库；文档/运维项使用可复核检查或演练结果。

## 开发准入与完成

开始前核对依赖已合并、范围/不做项、失败行为和外部参考。用 Given/When/Then 描述关键场景，例如“已有 revision 1，两个批次同时以 1 提交，只有一个成功，失败批次不推进游标”。未完成的依赖继续标明阻塞。

实现按 Red → Green → Refactor：先运行有意义的失败测试；做足够实现使其通过；保持行为不变整理代码，再运行适用回归。记录实际失败原因与结果，不把编译未通过、跳过测试或夹具错误当作需求红灯。签名提交、PR 与合并继续遵守 [贡献指南](../CONTRIBUTING.md)。

Rust 实现优先类型化状态/错误、清楚的所有权、无 panic 的输入路径和最小事务边界。外部 I/O 不进入数据库事务；批次限制与索引访问由测试/设计约束保障。性能优化须先有可重复基线、代表性输入和测量结果，不能从代码简化推导吞吐量提升。

完成时附 AC—测试映射、Red/Green 证据、检查结果及剩余限制。CI 成功不自动关闭父项或授权合并。当前实例见 [来源同步](source-sync.md)。
